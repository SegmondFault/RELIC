RELIC · API reference · as of 22 Nov 2026

How the RELIC API works

RELIC has no passwords. Every person and worker is an Ed25519 public key with one fixed role. You get an account by asking for one with your own key; a Moderator approves it with a signature. You log in by signing a one-time server challenge, and the account is found by the key alone. A session token only opens routes; anything that changes data must be signed by the account's key and is re-checked by PostgreSQL.

01Architecture and trust boundaries

* The API refuses to start against a non-local database without sslmode=require|verify-ca|verify-full. The signed formats live in crates/relic-crypto/src/auth.rs (Rust) and are mirrored in database/api/crypto.py; both sides are pinned to auth-v1.json test vectors.

02Identities and roles (RBAC)

An identity is a row in catalogue.user_public: a random User ID, a unique 32-byte public key, an owner type and a role. All four are immutable. Contact details (name, organisation, email) sit in user_private and are shown only to Moderators reviewing registrations. Nothing is deleted: a revoked account stays visible, marked revoked.

Roles are exclusive, not ranked: a Moderator cannot submit corpus data and an Analyst cannot flag. System accounts have no role and never get a session. Infrastructure admins run the server but have no RELIC identity, so server access never lets anyone sign as a user.

Every write passes four independent gates

A token decides which routes a caller can reach; it never authorises a write by itself. The signature is verified with the key registered for the claimed User ID, over versioned, domain-separated bytes, in the same transaction as the insert.

03Registration: bring your own key, a Moderator decides

Registering does not create an account. The applicant proves they hold a key and asks for a role; the request is pending until an active Moderator signs a verdict. RELIC never generates, receives or stores private keys.

The first Moderator and system accounts are created by the database operator as relic_owner (local-dev.sh bootstrap-moderator); the API cannot create them. decide_registration() is the only path by which relic_app can create a human account.

04Login: sign a challenge, identified by your key

The client names itself only by its public key; challenges are bound to no account. After login, GET /v1/me returns the User ID and role.

What the login answers, and why it leaks nothing

The signature is checked before any lookup, so without the private key every failure takes the same path and returns the same body. Issuing a challenge names no account, so it reveals nothing either.

05What exactly gets signed

Every signed message uses the same construction. Every field is length-prefixed (u64 big-endian), the record is hashed with SHA-256, and the digest is signed under a second, purpose-specific domain, so a signature for one purpose can never be replayed as another.

The server never trusts the nonce, expiry or audience a client sends back: it rebuilds the bytes from its own challenge row. Changing any field means a new v2 domain and new vectors, never editing v1.

Revocations use the same construction without a challenge. The Analyst signs revocation_id · analyst_id · target_type · target_id · reason under revocation-request:v1 / revocation-request-signature:v1; the client-chosen revocation_id is the row's primary key, so a signed request is stored once (identical retry → 200). The Moderator signs those five stored fields plus moderator_id · verdict under revocation-decision:v1 / revocation-decision-signature:v1. Both are verified with the registered key of the claimed User ID, which must be the caller. Flags work the same way: the Viewer signs flag_id · viewer_id · target_type · target_id · note under flag:v1 / flag-signature:v1; an Analyst's response signs flag_response_id, the five stored flag fields, analyst_id · note under flag-response:v1 / flag-response-signature:v1.

Known gaps (as of 23 Nov 2026)

GapEffect · direction
Signatures checked laterThe database does not verify signatures: a compromised API can still store forged user-signed rows. relic-verify detects them on its next run.
No key rotationKey = identity: a lost key means a new, unlinked account; a compromised key can only be revoked.
No per-token revocationNo logout; a stolen token works up to 8 h unless the account is revoked.
Per-IP, per-process limitsIPv6 hosts own a /64. Run one worker; limit per /64; cap open challenges.
Flag authors are publicAnyone sees who flagged what; kept so signatures stay verifiable.
Registration hygieneRejected keys may reapply indefinitely; pending requests never expire; emails are not verified; request rows (with PII) can never be deleted.
